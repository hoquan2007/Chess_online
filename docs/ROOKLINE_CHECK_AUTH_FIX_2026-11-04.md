## Diagnosis grounded in inspected evidence

1. The previous local chess presentation lacked a sufficiently obvious checked-king treatment and completed-game winner dialog. The development worktree now uses `checkedKingSquare` (`src/lib/chess/rules.ts`), red king-square emphasis and a screen-reader status in local/bot and online play, plus `GameResultDialog` on terminal results. Local chess finishes through chess.js; hosted games use the persisted server outcome, not user-provided winner/clock values.
2. The production deployment at inspection was `dpl_GMFKEH4J6L18mCQF3zwbypgr1hWG`, alias `https://chessonline-hnquan.vercel.app`, source `main` SHA `191d0a7485b1101431aa185af2a5cd897fdd1b19`. Inspecting that source showed the older callback with PKCE `code` handling only; it did not support `token_hash` confirmation links or offer email resend UX. The newer fixes exist on the development branch. Deployment READY and a lack of server error clusters do **not** demonstrate that email confirmation or login is working.
3. The existing production/preview Vercel settings list public Supabase URL/key and server-only Supabase key **by name**, but their values have not been disclosed or tested here. The remote Supabase Auth **Site URL**, **Redirect URL allow list**, confirmation template, email provider, message rate limits and actual inbox delivery have **not** been verified. Their misconfiguration is a **hypothesis**, not an established root cause. The Supabase project inspected was `tyvczicinpjixmxgjhjn`; do not apply migrations or change auth project settings as part of this frontend repair.
   Read-only Supabase Auth logs on November 4 provide narrower positive evidence: an earlier real signup returned HTTP 200, an outbound confirmation `mail.send` event was logged, and the subsequent `/verify` endpoint returned HTTP 303. Those requests originated from localhost; they do **not** prove that the recipient received email, the returned browser obtained a valid session, or the public production hostname succeeds. The logs also recorded a rejected synthetic `.test` signup (`email_address_invalid`) and rejected bad-JWT local requests; neither establishes a production mail-provider outage. Individual email addresses and tokens are intentionally omitted from this report.
4. Callback changes in `src/app/auth/callback/route.ts` now exchange PKCE `code` and accept supported `token_hash` types with Supabase `verifyOtp`. Both success and error paths use the allowlisted local return path (`safeNext`), and failed confirmation routes back to `/login?error=confirmation`. `AuthForm` supplies `emailRedirectTo` with the HTTPS origin and `/auth/callback?next=...`, explicitly prompts to verify, supports resend with 60-second UI cooldown, and maps email-unconfirmed errors to readable guidance.
5. The result overlay intentionally receives keyboard focus. Older browser tests that interacted with the obscured chess controls after game completion were updated to select **View board** or use **New game** within the dialog. This behavioral difference is an intended accessibility change.
6. Supabase's default confirmation template can also redirect to the app with tokens in a URL **fragment**, invisible to Next.js server routes. The callback now forwards no-code/no-token requests to `/auth/complete`, where a browser client validates the actual Supabase user/session, supports fragment tokens even if another account was previously signed in, removes sensitive URL fragments and navigates only to a safe same-origin path. Explicit callback errors still fail closed. The browser-based positive-path test intercepts the mock Supabase user endpoint and isolates first-party APIs; it does not demonstrate a valid hosted token.
